# Propensity Model: cross-sell / upsell next-best-offer pipeline

A production-style ML pipeline I built on my own Windows laptop to predict which business customers are most likely to take up a **new product** in the next 3 months, then rank the best offer per customer.
Everything runs on **synthetic data** generated by the repo itself. Nothing here uses real customer data.

**Products modelled (binary target each):** Current & Savings (CASA) | Term Loan | Funded Trade | Credit Card

## What it does

```
 raw drops (csv / xlsx)            stream (JSONL micro-batches)
        |                                   |
  batch ingestion + schema checks    consumer: validate -> bronze -> live signals -> stream PSI
        \_______________  bronze (parquet)  ______________/
                              |
          lookups -> product snapshots -> customer views -> rebasing (OW1..OW6 / PW1..PW3)
                              |
                  customer 360 mart (gold, ~700 columns)
                              |
     population + binary target -> WOE/IV binning -> variable selection (IV window + correlation pruning)
                              |
     6 models per product  ->  champion (out-of-time Gini)  ->  MLflow tracking + registry (alias: champion)
                              |
     score -> calibrated propensity x revenue potential -> eligibility filter -> ranked offers
                              |
     monitoring: PSI (score) | CSI (WOE bins) | KS (raw features) | schema + null checks | Evidently HTML
                              |  retrain trigger -> retrain -> re-score
                    FastAPI  (/score, /api/prospects, /api/drift ...)  +  HTML dashboard
```

Orchestrated by **Airflow** (batch DAG daily, stream DAG every 5 min). The same CLI also runs everything by hand with no Docker.

## Quick start (Windows, PowerShell)

```powershell
git clone https://github.com/Akshaydoc/Propensity-Model-.git
cd Propensity-Model-
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt

python -m csu.cli run-all          # generate data -> ingest -> features -> train 4 products x 6 models -> score -> monitor (~3 min)
uvicorn api.main:app --reload      # dashboard: http://127.0.0.1:8000   API docs: http://127.0.0.1:8000/docs
mlflow ui --backend-store-uri sqlite:///mlflow.db     # experiments + model registry: http://127.0.0.1:5000
```

Step by step instead of `run-all`:

| Command | What it does |
|---|---|
| `python -m csu.cli generate --customers 3000` | synthetic tables to `data/raw` (csv) + `sample_input.xlsx` |
| `python -m csu.cli ingest` | csv/xlsx -> schema validation -> `data/bronze` (bad rows go to `data/quarantine`) |
| `python -m csu.cli features` | customer views, OW/PW rebasing, customer 360 |
| `python -m csu.cli train [--product credit_card] [--mode upsell]` | WOE, 6 models, champion, MLflow |
| `python -m csu.cli score` | ranked offers -> `data/gold/recommendations.parquet`, `reports/next_best_offer.csv` |
| `python -m csu.cli monitor [--drift-demo] [--auto-retrain]` | PSI/CSI/KS/schema + Evidently + retrain decision |
| `python -m csu.cli stream-produce --events 500 [--drift]` | simulate the upstream event feed |
| `python -m csu.cli stream-consume` | validate + append a micro-batch, stream drift check |
| `python -m csu.cli stream-compact --ym 202507` | roll stream events into the monthly txn tables |

Run the tests with `pip install -r requirements-dev.txt` then `python -m pytest -q` (14 tests, about 30 s).

## Design choices

- **Data layers:** raw -> bronze -> silver (lookups) -> gold (customer views, 360 mart, recommendations).
- **Windows:** OW1..OW6 are the 6 observation months (OW1 = reference month), PW1..PW3 the next 3 performance months. For every metric the pipeline generates mean/std/max/min/sum/median/growth/volatility/recency/frequency and point-in-time flags.
- **Target:** *cross-sell* = customer holds none of the product across OW1..OW6 and acquires it in PW1..PW3. *Upsell* (`--mode upsell`) = holder whose balance in PW3 is at least 1.2x OW1. Both are binary.
- **Population rules:** relationship of at least 7 months, no delinquency, at least one active product at the reference month, plus a policy table (min relationship, min age, allowed segments, blocked industries) at scoring time.
- **Engine:** pandas + parquet. I skipped PySpark on purpose: it needs Java and winutils on Windows and gains nothing at this size. The code is vectorised so a Spark port is straightforward.
- **Streaming:** a file-based micro-batch queue (landing folder of JSONL files). It is free, needs no broker, and works on Windows and on free cloud tiers. Only `_read_batches` changes to move to Kafka/Redpanda.

### Weak spots from the earlier pipeline design that I fixed

| Gap | Fix here |
|---|---|
| IV cut-off effectively switched off | real window: IV between 0.02 and 0.60 (drops weak and leakage-suspicious variables), then correlation pruning at 0.85, max 12 features |
| Non-events from one month, events from many | every observation month is used for both classes |
| Same customer could sit in train and test | split is by customer; out-of-time set starts 3 months after the dev window so performance windows never overlap |
| Fixed 0.5 threshold on a 5% event rate | F1-optimal threshold tuned on the test split, plus decile lift / capture reporting |
| Class imbalance ignored | cost-sensitive sample weights |
| Raw scores are not probabilities | isotonic calibration on the test split, used for expected value |

## Results (synthetic data, 3,000 customers, seed 42)

| Product | Champion | Test Gini | Out-of-time Gini | OOT KS | Top-decile lift | Top-20% capture |
|---|---|---|---|---|---|---|
| Term Loan | AdaBoost | 0.58 | 0.49 | 0.38 | 4.1x | 55% |
| Funded Trade | Logistic Regression | 0.54 | 0.46 | 0.34 | 3.5x | 47% |
| Credit Card | Logistic Regression | 0.39 | 0.40 | 0.30 | 2.9x | 44% |
| Current & Savings | AdaBoost | 0.30 | 0.16 | 0.16 | 1.7x | 28% |

Exact figures vary slightly by library version. Each run writes the full 6-model comparison to `reports/<product>_cross_sell/metrics.json`.
Current & Savings is the weakest: its eligible population is small (about 140 out-of-time events), so the out-of-time estimate is noisy. I left it as is rather than tune the synthetic data to flatter it.
Upsell mode runs end to end, but the generator's balances follow a random walk, so there is almost no learnable upsell signal. With real data that changes.

## Monitoring and retraining

| Check | Rule |
|---|---|
| Score PSI | warn at 0.10, alert at 0.25 |
| CSI per WOE-binned feature | alert at 0.25; 3 or more alerting features triggers retrain |
| KS test per numeric feature | flagged when p < 0.01 and statistic > 0.1 |
| Schema / data quality | missing or non-numeric features block scoring; null rate over 30% and unseen categories warn |
| Performance | Gini on the latest matured months vs the champion's out-of-time Gini; drop of 0.10 or more triggers retrain |
| Evidently | HTML data-drift report per product in `reports/monitoring/` |

`python -m csu.cli monitor --drift-demo` shifts the model inputs on purpose to show the ALERT and retrain path. `--auto-retrain` retrains automatically when a trigger fires. Thresholds live in `config/config.yaml`.

## Free cloud deployment

The root `Dockerfile` builds a small demo model set at image build time and serves the dashboard and API on `$PORT` (default 7860).

- **Hugging Face Spaces (Docker):** create a Docker Space, push this repo, and add this header at the top of that Space's README: `sdk: docker` and `app_port: 7860` between `---` lines.
- **Render:** New > Blueprint > pick this repo (`render.yaml`, free plan). The free tier sleeps when idle.


## Limitations

- Synthetic data: metrics show the pipeline works, not real-world performance.
- The Airflow DAGs and docker-compose were syntax-checked but I have not run them in a live Airflow here; test them on your laptop first.
- Models are untuned defaults; the focus is the pipeline, not squeezing the last point of Gini.
